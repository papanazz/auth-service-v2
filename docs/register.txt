REGISTER
========

POST /v1/user/register

Creates a new identity. Does not authenticate the caller — register and
login are separate steps; this endpoint returns no tokens.


FLOW
----

internal/app/user/register/service.go — RegisterService.Handle

  1. Normalize and validate input
       email is lowercased and trimmed. Validate() (validator.go) rejects
       anything net/mail can't parse.

  2. Enforce password policy
       platform/password.Policy: minimum 8 characters, at least one
       uppercase, one lowercase, one digit. See docs/login.txt for why this
       lives in platform/ instead of domain/ — same reasoning applies here.

  3. Reject a duplicate account
       FindByEmail against the normalized address. This check is racy
       against a concurrent registration for the same email — the
       database's UNIQUE constraint on users.email is the real guarantee.
       The check exists to turn the common case into a clean
       USER_ALREADY_EXISTS instead of a raw constraint-violation error
       reaching the client. A true race still ends in one winner and one
       constraint-violation 500 for the loser; nothing here retries or
       maps that error specifically (see GAPS).

  4. Hash the password and persist the account
       Argon2id (platform/password/argon2id.go): 64 MiB memory, 3
       iterations, 2 threads, 16-byte salt, 32-byte key — parameters live
       on the Argon2id struct, not config, since changing them changes
       every future hash's cost and isn't something to vary per
       deployment.

       The account is built via user.New(), then Status is immediately
       forced to ACTIVE. See DECISIONS.

  5. Publish audit event
       USER_REGISTERED, success=true, with the account's email/IP/user
       agent. Best-effort (errors are swallowed) — an audit outage must
       not fail a registration that already succeeded. Only the success
       path is audited; see GAPS.


DECISIONS
---------

* Accounts are created ACTIVE, not PENDING, despite user.New() defaulting
  to PENDING and the domain model clearly being shaped for an email
  verification flow (EmailVerifiedAt, VerifyEmail(), the PENDING status
  itself). There is no verification token, no delivery mechanism, and no
  endpoint to complete verification — shipping PENDING today would
  permanently strand every new account with no way to ever reach ACTIVE.
  service.go overrides the status explicitly, with a comment pointing
  here. This is the single highest-priority item in GAPS.

* Duplicate-email detection is a pre-check, not a caught constraint
  violation. This mirrors the login device-collision code's original
  shape before that was hardened (see docs/login.txt) — accepted here
  because losing the race just surfaces as a 500 on a call the client
  will typically retry with a different email anyway, not a silent
  security or data-integrity issue.

* register.Command carries IPAddress/UserAgent (added during this review)
  so the audit event has the same client context login's does. The HTTP
  handler fills them from r.RemoteAddr / r.UserAgent(), same as
  handler/auth.go.


CAPABILITIES
------------

* Case/whitespace-insensitive email normalization, applied identically at
  registration and later at login (both call the same lowercase+trim
  shape independently — see docs/login.txt GAPS for the duplication).
* Password policy enforcement (platform/password.Policy).
* Argon2id password hashing — the raw password never reaches the
  repository or the database.
* Audit trail entry (USER_REGISTERED) with email, IP, and user agent.
* User enumeration is not specifically defended here the way login
  defends it (dummy-hash verification on unknown accounts): a duplicate
  email returns USER_ALREADY_EXISTS, which is an intentional trade-off —
  the endpoint's job is to tell the caller whether an email is already
  taken.


GAPS (known, deliberate, not implemented in this pass)
-------------------------------------------------------

* Email verification. user.New()/VerifyEmail()/EmailVerifiedAt exist in
  the domain model; nothing in this service uses them beyond the status
  override. Building this out requires: a verification token + TTL, an
  email delivery mechanism (none exists in this repo — no
  platform/email package), a verify endpoint, and login gating on
  EmailVerifiedAt. Out of scope for this review; flagged as the natural
  next capability if this project needs to look more production-shaped.

* Failure-path auditing. Only a successful registration is published.
  A duplicate-email attempt is a real security signal (account
  enumeration) but audit.EventType has no failure constant for
  registration the way EventLoginFailed exists for login, and adding one
  is a small but real scope expansion beyond wiring up what already
  existed. Noted, not done.

* The duplicate-email pre-check's race loses to a 500 instead of a mapped
  409/USER_ALREADY_EXISTS. Low priority: the constraint still protects
  data integrity, this only affects the error shape returned to the
  loser of a true concurrent double-submit of the same email.


CROSS-CUTTING FIX LANDED DURING THIS REVIEW
--------------------------------------------

internal/platform/postgres/repository/audit/mapper.go — parseIP() didn't
strip the port from http.Request.RemoteAddr before calling
netip.ParseAddr, so it silently failed and stored NULL for every event's
IP address, for every endpoint, since audit logging was introduced. The
session repository had already hit and fixed this exact bug (see its
TestParseIP). Ported the fix here with the same regression test. This is
why register's audit event above is the first one in the codebase with a
correct, non-null ip_address.


API CONTRACT
------------

Request

  POST /v1/user/register
  Content-Type: application/json

  {
    "email":    string,  required, valid RFC 5322 address
    "password": string,  required, >=8 chars, upper+lower+digit
  }

Success — 201 Created

  {
    "data": {
      "id":    string (UUID),
      "email": string (normalized: lowercased, trimmed)
    }
  }

Errors

  400 INVALID_REQUEST       malformed JSON body
  400 INVALID_EMAIL         email missing or not a valid address
  400 WEAK_PASSWORD         password fails the policy
  409 USER_ALREADY_EXISTS   email already registered
  500 INTERNAL_ERROR        unexpected failure (hashing, DB, ...)

No authentication required. No rate limiting on this endpoint currently
(login has IP/credential rate limiting via platform/authattempt; register
does not — a gap worth noting if abuse becomes a concern, not fixed here).


TESTED SCENARIOS
-----------------

Unit — internal/app/user/register/service_test.go (table-driven +
dedicated tests, run via `go test ./internal/app/user/register/...`):

  - registers a new account
  - normalizes email casing and surrounding whitespace
  - rejects a malformed email
  - rejects a password the policy refuses
  - rejects an email that already exists
  - propagates an unexpected lookup failure
  - propagates a hashing failure
  - propagates a create failure
  - persists the normalized account with a hashed password, ACTIVE status,
    no EmailVerifiedAt, and an ID matching the returned result
  - publishes USER_REGISTERED with the correct user ID, email, IP, and
    user agent on success
  - does NOT publish an audit event when registration fails

e2e — against the real docker-compose stack (postgres + redis), verified
manually this session:

  - POST /v1/user/register with a fresh email → 201, well-formed body
  - Immediately re-registering the same email → 409 USER_ALREADY_EXISTS
    (implied by the flow; also covered at the unit level)
  - Audit row created with type=USER_REGISTERED, success=true, correct
    email, and — after the parseIP fix — a correct, non-null ip_address
    and user_agent
  - Full lifecycle sanity: register → login → refresh → logout all still
    succeed end-to-end after every change in this review pass
